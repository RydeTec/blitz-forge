Modern Features 

BlitzForge is drop-in source-compatible with classic Blitz3D, but adds a set of modern language extensions. Everything on this page is additive — existing programs keep working, and you opt in to the new features only where you want them.

Every example below is taken from the BlitzForge test suite (the tests/ directory), so each one compiles and runs with the current toolchain. The test file each feature is drawn from is noted alongside it.

Strict mode

Placing Strict on the first line of a file turns on stricter checking: variables must be declared (with Local or Global) before use, and type rules are enforced more tightly. Strict is the gateway to the modern feature set — most new code begins with it.

Strict

Local count% = 0
count = count + 1
Print count

Strict is per file and is the recommended default for new code. Legacy (non-Strict) programs continue to behave exactly as they did in Blitz3D.

Garbage collection

BlitzForge can automatically reclaim type objects for you using reference counting. Enable it with EnableGC (which requires Strict mode), and you no longer have to Delete every object by hand. DisableGC turns it back off, and NoTrace opts a file out of debug tracing.

Strict
EnableGC

Type TestType
    Field var
End Type

Local t.TestType = New TestType()
; RefCount reports the object's tracked reference count
Print RefCount( First TestType ) ; prints 1

An object is released automatically when the variable holding it goes out of scope (or is reassigned). RefCount lets you inspect an object's tracked reference count. Note that the count follows the object's lifetime binding, not every alias: binding a second variable to the same object does not raise its RefCount, and field assignments are not counted. A practical consequence is that a reference cycle — two objects pointing at each other through fields — is still collected when the holding variables leave scope (the field back-references add no counts), so cycles do not leak. Keep a live variable referencing anything you need to retain. (see the contract pinned in tests/GarbageCollectionTest.bb)

Type inheritance

A type can extend another type by naming the parent with a . tag in its declaration: Type Child.Parent. The child inherits the parent's fields and can add its own. A child instance can be assigned to a variable of the parent type (an implicit "down-cast" to a more general type).

Strict
EnableGC

Type Base
    Field baseVar$
End Type

; Inherit extends Base — it gets baseVar plus its own inheritVar
Type Inherit.Base
    Field inheritVar$
End Type

Local child.Inherit = New Inherit()
child\baseVar = "foo"    ; inherited field
child\inheritVar = "bar" ; own field

; Assigning a child to a parent-typed variable is allowed
Local asBase.Base = child

(tests/InheritTest.bb)

Methods

Types can carry behaviour as well as data. A Method is a function that runs against a particular instance, available inside the method as self. Methods can be called dynamically on an instance (instance\method(..)) or statically (Type::method(instance, ..)), and a child type can override a parent's method.

Strict
EnableGC

Type TestStruct
    Field testVar$
    Method testMethod( testArg$ )
        self\testVar = testArg
    End Method
End Type

Local inst.TestStruct = New TestStruct()

; Dynamic call
inst\testMethod( "buzz" )

; Static call — pass the instance explicitly
TestStruct::testMethod( inst, "bar" )

A common idiom is a constructor method that initialises fields and returns self, so a type can be created and populated in one expression:

Type ConstructorTest
    Field value1$
    Method create.ConstructorTest( value1$ )
        self\value1 = value1
        Return self
    End Method
End Type

Local instance.ConstructorTest = New ConstructorTest( "value1" )

(tests/MethodTest.bb)

Recast

Assigning a child instance to a parent-typed variable is automatic, but going back the other way — treating a parent-typed reference as the child type again — needs an explicit Recast. Recast.Type(expr) performs a runtime "is-a" check against the target type's inheritance chain: if the object really is an instance of that type it is returned, otherwise Recast returns Null. Always check for Null before dereferencing.

Local child.Inherit = New Inherit()
Local asBase.Base = child    ; down-cast (automatic)

; Up-cast back to the real type (explicit)
Local backAgain.Inherit = Recast.Inherit( asBase )

; A cast to a type the object is NOT returns Null rather than
; reinterpreting the bytes:
Local wrong.SecondInherit = Recast.SecondInherit( asBase )
If wrong = Null Then Print "not a SecondInherit"

(tests/InheritTest.bb)

Continue

Continue skips to the next iteration of the enclosing For, While or Repeat loop — the counterpart to Exit, which leaves the loop entirely.

Local sum = 0
For i = 0 To 10
    If i = 5 Then Continue ; skip 5
    sum = sum + i
Next
Print sum ; 50

(tests/LoopTest.bb)

Function pointers

BlitzForge can take a reference to a function and call it indirectly. The @ sigil marks a function-pointer type; BBFunction is the type of a pointer; and a function returns a pointer to itself by calling FunctionPtr(). Because indirect calls pass a single value, anything richer is wrapped in a small "DTO" (data-transfer object) type and passed via Ptr.

Strict
EnableGC

Type BasicDTO
    Field var%
    Method create.BasicDTO( var% )
        self\var = var : Return self
    End Method
End Type

; A pointer-returning function: when handed Null it returns its own pointer
Function myFunc@( dto.BasicDTO = Null )
    If dto = Null Then Return FunctionPtr()
    Return New BasicDTO( dto\var )
End Function

Local f.BBFunction = myFunc( Null )
Local result.BasicDTO = Call( f, Ptr New BasicDTO( 1 ) )

(tests/FunctionPointerTest.bb)

Asynchronous calls

A function pointer can be launched on its own thread with Async, which returns a BBThread future immediately so the main thread keeps running. Await blocks until the result is ready and returns it; Poll checks whether it is ready without blocking; and AsyncThen chains a second function to run on the result of the first.

Local f.BBFunction = myFunc( Null )

; Launch — returns a future straight away
Local thread.BBThread = Async( f, New BasicDTO( 2 ) )

; ... do other work here ...

; Check without blocking
If Poll( thread )
    Local result.BasicDTO = Await( thread )
End If

; Or chain a follow-up function onto the result
Local chained.BBThread = AsyncThen( thread, anotherFunc() )

This is a fragment for illustration; see tests/FunctionPointerTest.bb for complete, runnable async examples.

Exceptions: Throw and TryCatch

BlitzForge supports error handling through Throw and TryCatch. TryCatch(tryFn, catchFn, dto) runs the try function; if it (or anything it calls) Throws, control transfers to the catch function, which receives the thrown payload. Both functions and the payload are passed as function pointers / DTO objects, mirroring the function-pointer calling convention above.

Function functionToThrow@( dto.BasicDTO = Null )
    If dto = Null Then Return FunctionPtr()
    Throw New BasicDTO( 10 ) ; transfers control to the catch fn
    Return New BasicDTO( 1 )
End Function

Function functionToCatch@( code.BasicDTO = Null )
    If code = Null Then Return FunctionPtr()
    ; code\var holds the thrown payload (10 here)
    Return New BasicDTO( 2 )
End Function

Local dto.BasicDTO = New BasicDTO( 0 )
Local t.BBFunction = functionToThrow()
Local c.BBFunction = functionToCatch()
Local result.BasicDTO = TryCatch( t, c, dto ) ; result\var = 2

(tests/TryThrowCatchTest.bb)

Pointers

The Ptr operator takes a typed pointer to an object, and BBPointer (or the @ sigil on a variable) is the type of a pointer. Pointers let you pass objects through interfaces that work in terms of raw references — for example the function-pointer calling convention shown above.

Strict
EnableGC

Local bank.BBBank = CreateBank( 4 )
Local p1.BBPointer = Ptr bank  ; explicit BBPointer type
Local p2@ = Ptr bank      ; @ is shorthand for a pointer

; A pointer refers to the same underlying object
ResizeBank p1, 16
Print BankSize( bank ) ; 16

(tests/PointerTest.bb)

The built-in test framework

BlitzForge has a unit-test runner built into the compiler. A Test name() ... End Test block is a test; Assert(expr) checks a condition (and returns the boolean result so it can be used inline). Run every test in a file with blitzcc -t file.bb.

Strict
EnableGC

Test AdditionTest()
    Assert( 1 + 1 = 2 )
End Test

The test suite under tests/ is the authoritative, executable specification for all of the features on this page.
